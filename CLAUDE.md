# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

FFT-TFA is a research-notes repository developing FFT-accelerated Transformation Field Analysis (TFA) for elastoplastic composite homogenization. `code/` holds a single Python file (`MAIN.py`) that is being built up step by step. The offline stage is complete: it goes from the mesh through `E`, `P` and `P₀`, which are cached on disk. The whole online stage (`get_plastic_eigenstrain`, `standard_richardson_iteration`, `fft_preconditioned_richardson_iteration`) is still a `pass` stub, and `main` does not call it yet. There is no dependency manifest, linter, or test suite. The code needs Python with numpy and scipy (`scipy.sparse` and `scipy.sparse.linalg`, added for the sparse `K` and its `splu` factorization; the local environment has Python 3.12, numpy 1.26 and scipy 1.11). Check with the user before adding other dependencies or commands here. Functions are checked with throwaway scripts in the scratchpad (patch tests, symmetry, null-space counts, and the E/P identities listed below), not with tests added to the repo.

Run it with `python3 code/MAIN.py`. `main()` computes or loads `E`, `P`, `P₀` (printing which for each cache file), then stops: it keeps them in local variables and does not use or return them yet, so a clean run prints only the cache messages. That is expected, not a bug to chase.

Cost matters when testing. At 9 elements and 3 partitions per side (the config default) a cold run takes about 1.6 s, and a cached run is instant. At 18/6 a cold run takes about 3.4 minutes. The user's target is 27/9 (59,049 displacement DOFs, 729 partitions): factoring `K` and solving 6 right-hand sides took 255 s and 4.7 GB peak, but a full 27/9 run has not been done. The full eigenstrain solve (4,374 columns, done once for `E`/`P` and once for `P₀`) is untimed, and its memory (a dense `F_eigenstrain` and displacement array of about 2 GB each, plus the LU factors, against roughly 8 GB free) is an open risk. Test logic at 9/3, changing a parameter that exercises the same path when the config checks forbid varying the one you first thought of, and run anything long with `run_in_background`.

## Layout

- `notes/Formulation.md` — the main synthesis document: derives the actual eigenstrain/plasticity (E/P) partition-strain relation (Fish–Cui) and two solution strategies — a Moulinec–Suquet-style FFT fixed-point iteration, and a Ladecký-style reference-preconditioned Newton–Krylov (GMRES) solve.
- `notes/verified_notes/` — a sequential derivation chain building up to `Formulation.md`. Read via its own `README.md`, which gives the intended reading order (influence functions → partitioned eigenstrain → partition-average strain transformation → nonlinear FEM/Newton structure → J2 yield/flow/hardening → elastic trial and radial return → complete J2 return-mapping algorithm).
- `references/` — source PDFs cited by the notes: Fish & Cui on eigenstate-based homogenization, Dvorak 1992, a computational plasticity text, Fish's practical multiscaling, the original Moulinec–Suquet paper, and the Ladecký et al. FFT-preconditioned FE solver paper. All citation links in the notes point at these local copies.
- `code/MAIN.py` — the sole implementation file: a config block of RVE/material/loading parameters (domain and inclusion size, element and partition counts per side, elastic moduli, J2 yield stress and hardening modulus, strain steps, fixed-point tolerance), then the functions, then `main`. `code/cache/` (gitignored, created on first run) holds the cached operators. The later stubs (`get_plastic_eigenstrain`, `standard_richardson_iteration`, `fft_preconditioned_richardson_iteration`) map onto `Formulation.md`'s strategy 1 (the local J2 return map ER-3 following `verified_notes/07`; the un-preconditioned baseline ER-4/ER-11 with θ=0, Section 11; the FFT reference solve ER-15). There is no code yet for strategy 2 (Newton–Krylov, Section 8).

## How MAIN.py is organized

The offline stage, which produces the influence operators, is finished. Its design choices are settled and are not obvious from reading the code:

- **Influence operators come from a finite-element solve, not from a Fourier kernel.** `main` builds a periodic 3D hexahedral mesh, the strain-displacement matrix `B`, a per-material stiffness (`get_L`, 6×6) and then a per-element stiffness array (one 6×6 per element, from element material ids: 0 = matrix, 1 = inclusion). `get_influence_functions(B, L_per_element, element_nodes, element_partition_ids)` builds `K` (`get_K`) and two load sets, `get_F_macrostrain` (unit macro-strain) and `get_F_eigenstrain` (unit eigenstrain in each partition), then calls `solve_influence_function(K, F, ...)` once per load set. That helper chains `solve_for_displacements` (`K d = F`) and `get_partition_average_strain` and returns the partition-average *fluctuation* strain. These are ST-10/ST-11 and ER-24.
- **The identity is added to `E` only, in `get_influence_functions`.** ST-10 defines `E^B = I + average(B d)` and ST-11 defines `P^{BA}` with no identity, so `solve_influence_function` stays generic and `E` is the stacked 6×6 identity plus its result. Shapes: `E` is (6M, 6), `P` and `P₀` are (6M, 6M), with M = partitions per side cubed. Blocks are partition-major: row block `B` (`6*B … 6*B+5`), column block `A`, so `F_eigenstrain` column `6*A + s` is unit eigenstrain component `s` in partition `A`.
- **Load signs live inside `F`**, so the solve is always `K d = F`: `F_macrostrain = −∫BᵀL` (IF-A7) and `F_eigenstrain = +∫_{Θ^A} BᵀL` (IF-A8, piecewise-constant partition eigenstrain). Both share `get_F_element`, which is `weight · Σ_g B[g]ᵀ L`.
- **`P₀` is the same function called a second time** with one uniform reference stiffness in every element (`reference_L` in `main`, currently a placeholder equal to the matrix stiffness). This keeps `P₀` consistent with the discretization and avoids implementing the Fourier Green operator or its sign convention. By ER-25, scaling `reference_L` does not change `P₀`; only its Poisson ratio or anisotropy does.
- **`E` and `P` are the partition strain-influence matrices `E^B`, `P^BA` of the notes**, not Young's modulus or pressure; Young's modulus is `elastic_modulus_*` in the config.
- **Standard end-to-end checks** (each verified numerically, and all follow from the notes): the mean of `E^B` over partitions is `I` (IF-M7); the mean over `B` of each `P^{BA}` is 0 (IF-M6); `E^B + Σ_A P^{BA} = I` (a uniform eigenstrain equal to the macro-strain produces no fluctuation); with a uniform stiffness `E = I` and `Σ_A P₀^{BA} = 0`; and the eigenvalues of `P₀` lie in [0, 1] (Formulation.md Section 11).
- **Geometry**: 3D, with element and partition counts per side set in the config. The default is 9 and 3, and the user is moving to 27 and 9. The inclusion is always domain / 3 on a side (volume fraction 1/27): the centre partition at 3 per side, the central 3×3×3 block of partitions at 9 per side. Each partition must hold a single material, so inclusion edges must fall on partition edges (and element edges); the config block enforces this with two checks (elements per side divisible by partitions per side, and the centred inclusion having a whole number ≥ 1 of matrix partitions on each side). At 3 partitions per side that leaves domain / 3 as the only valid inclusion size. Element materials come from element-centre geometry, and all indexing code is written in terms of the config counts rather than literal 9 or 3. Only the matrix yields; the inclusion stays elastic.
- **Indexing and ordering** (settled, shared by every function): x-fastest everywhere, `id = i + count_per_side*j + count_per_side**2*k` via `get_grid_id`, for nodes, elements and partitions. Hex8 corners use the same rule with count 2 (corner = a + 2b + 4c), not the textbook counter-clockwise order. Displacement DOFs are component-fastest: DOF = component + 3·node, and `get_element_dofs` returns each element's 24 global DOFs in that order. Prefer x-fastest ordering wherever an ordering choice comes up.
- **`B` and element integration**: `get_B` returns one array of shape (8, 6, 24), B at the 2×2×2 Gauss points (natural coordinates ±1/√3, weights 1, jacobian `gauss_point_volume_weight` = h³/8). It is identical for every element because all elements are the same cube. Rows follow the ER-2 order (11,22,33,12,23,13) with engineering shear; columns are [u1,u2,u3 of corner 0, then corner 1, …]. The load and strain-average functions should reuse the same Gauss points and weight.
- **`K`** is a scipy sparse CSR matrix, (3·n³)² with n elements per side (periodic: n³ unique nodes; 81 entries per row). `get_K` fills one (24, 24) block per element from `get_K_element` (weight · Σ_g Bᵀ L B), builds each entry's global row and column from `get_element_dofs` with `np.repeat` and `np.tile`, and lets `coo_matrix(...).tocsr()` sum the entries that elements share. Dense `K` is not an option at 27 per side (about 28 GB). It has exactly 3 zero modes (rigid translations; the periodic wrap removes rotations).
- **`solve_for_displacements`** pins node 0 (DOFs 0–2) instead of imposing the notes' zero-mean condition (IF-M2); the two differ by a constant displacement, so strains, `E` and `P` are identical. It slices out the free DOFs, converts to CSC, factors once with `scipy.sparse.linalg.splu`, and solves the right-hand sides 100 columns at a time to keep temporary arrays small. The factorization stays local to the function and is never returned.
- **The offline results are cached** in `code/cache/E_P.npz` (`E` and `P`) and `code/cache/P0.npz` (`P₀`), through `load_cache` and `save_cache` in `main`. Each file stores its key parameters next to the arrays and is reused only if every one matches exactly; otherwise it is recomputed and overwritten, with a printed message naming the first parameter that differs. `E_P.npz` is keyed on the domain size, inclusion size, element and partition counts, and the matrix and inclusion stiffness matrices; `P₀.npz` is keyed on the domain size, element and partition counts, and `reference_L`, so it survives a change of inclusion size. The keys use the 6×6 stiffness matrices, not the moduli and Poisson ratios, so replacing the placeholder reference is picked up automatically. Loading and plasticity settings (strain steps, yield stress, hardening, tolerance) are deliberately not in any key. The key does not cover changes to the offline code itself (element formulation, load assembly): delete `code/cache/` after such a change.

## Working on MAIN.py

The user is building this deliberately, to understand the motivation for every function. Follow their process:

- Work top-down and demand-driven: write the caller as a short wish-list of calls, stub what it needs with `pass`, then implement leaf functions first, one small step at a time. Don't implement ahead of what was asked, and don't write code when told not to.
- Before writing each function, describe it in chat (what it returns and its shapes, new helpers, the checks you will run) and wait for the go-ahead; the user often says "no code yet" while planning.
- Readability comes first. Use descriptive names; avoid opaque single-letter operators beyond the notation already in use (`E, P, K, F, B, L`), and avoid clever abstractions such as returning factorization objects or callables. Names must say what the thing is: vague ones like `factors` or `hex8_corner_signs` were rejected in favour of `xi_bracket` and `corner_natural_coordinates`. Derived names follow the notation (`K` → `K_element`, `get_K_element`).
- Spell the maths out rather than compressing it: three explicit derivative lines were preferred over a loop with an `other_directions` list, and small explicit corner arrays over index tricks. Deep loop nests were tolerated once the user was asked; don't refactor them unprompted.
- **Do not add comments or docstrings** to `MAIN.py`; the user writes them. Explain shapes and reasoning in chat instead.
- Everything stays in `MAIN.py` for now; don't split it into modules.
- Keep code changes minimal, and estimate a test's cost before running it: use the cheapest size (9/3) that exercises the logic, and send long runs to the background.
- Equations in chat are shown as unicode in code blocks (LaTeX does not render in the user's view).

## Conventions

- **Equation labeling is per-file and load-bearing.** Each note file has its own prefix: `IF-` (01, displacement influence functions), `P-` (02, partitioned eigenstrain), `ST-` (03, partition-average strain transformation), `EN-` (04–05, elastoplastic FEM/Newton structure and J2 yield/flow/hardening — this prefix spans two files), `RR-` (06, elastic trial and radial return), `RM-` (07, complete J2 return-mapping algorithm), and `ER-` in `Formulation.md` for the actual E/P relation and its two solvers. Cross-references between files cite these labels directly (e.g. `Formulation.md` builds on `ST-` results from `03_partition_strain_transformation.md`). When editing derivations, preserve existing labels and continue the numbering scheme rather than renumbering.
- **Engineering strain/stress vector convention** (defined in `Formulation.md`, Equation ER-2): strain uses engineering shear (`2ε₁₂` etc.), stress uses physical shear, so their dot product is mechanical work. Every operator across the notes must respect this convention.
- **Sign convention for the reference Green operator**: this repo's `Γ⁰` is the *negative* of the standard Moulinec–Suquet strain Green operator (`Γ⁰_MS = -Γ⁰`). This is called out explicitly wherever Fourier formulas are quoted from the literature — preserve the stated sign when adding or checking equations.
- **Notes must be self-contained.** Every link/citation in `notes/` must resolve to a file actually present in this repo (no local machine paths, no links to not-yet-created companion code or planning docs like a syllabus/reference guide). If you cite external literature, add the PDF to `references/` and link to it there, or cite it as plain text without a link.
- `.gitattributes` sets `* text=auto eol=lf`, so files are normalized to LF line endings, including when working from WSL on a Windows checkout.
